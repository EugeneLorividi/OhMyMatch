# Технічне завдання: OhMyMatch MVP (веб, без Telegram)

18 жовтня 2026 · @Lorividi

Зміни: 8 листопада 2026 — додано обмін Telegram-ніком між метчами (розділи 1–4, 6, 8–12).

## 1. Мета й контекст

OhMyMatch — закритий вебзастосунок, який підбирає людей з однієї спільноти одне одному за результатами тесту bdsmtest.org. Ця версія ТЗ охоплює вебчастину й обмін Telegram-ніком між метчами; Telegram-бот описується окремим ТЗ.

- **Аудиторія:** закрита спільнота, кілька сотень користувачів, усі 18+.
- **Власного тесту немає.** Людина проходить bdsmtest.org і приносить результат: вставляє текст списку або завантажує скриншот.
- **Дані особливої чутливості.** Стать, орієнтація та інтимні вподобання — персональні дані особливої категорії. Застосунок псевдонімний, а не анонімний, і саме так чесно називає себе на сторінці «що ми зберігаємо».
- **Принцип:** зберігаємо лише те, без чого не працює підбір. Жодних скриншотів на диску, вихідного тексту вставки, email, телефонів, фото, біографії та вільного тексту. Єдине виняткове поле — необов’язковий Telegram-нік: його перевіряють за суворим шаблоном, зберігають лише в зашифрованому вигляді й показують метчу тільки за взаємної згоди (розділ 8).
- **Платних API не використовуємо.** OCR і розбір працюють локально, без звернень до Claude API та зовнішніх сервісів.

## 2. Межі MVP

Перша версія охоплює повний шлях від реєстрації до взаємного метчу, без Telegram. Усе, що не ввійшло, явно відкладено, а в схемі даних для нього залишено заділ і заглушки.

**Входить:**

- реєстрація за запрошенням, підтвердження 18+, згода;
- профіль: «хто я», «кого шукаю», режим пошуку;
- введення результату тесту: вставлення тексту й розпізнавання скриншота, з обов’язковим підтвердженням;
- список «ні» (чого я точно не хочу);
- підбір: жорсткі фільтри, звичайний і експериментальний режими, пояснення збігу;
- лайки, пропуск, блокування, взаємний метч;
- необов’язковий Telegram-нік і взаємний обмін ним у картці метчу;
- видалення акаунта, сторінка «що ми зберігаємо».

**Відкладено (зараз не робимо):**

| Що | Чому відкладено | Заділ у MVP |
| --- | --- | --- |
| Telegram-бот | окреме ТЗ | клас ContactGateway, до якого бот підключиться згодом |
| Перевірка своїх | окреме рішення | коди запрошень через CLI |
| Режим «за роллю» (саб шукає домінанта тощо) | доопрацюємо після запуску | nullable-поле focus у users, логіки немає |
| Цикл «як усе пройшло» після контакту | потрібен контакт через бота | таблицю не створюємо, описано в розділі 6 |
| Юридичне опрацювання | рішення власника | сторінка «що ми зберігаємо», згода з версією |

## 3. Стек, репозиторій і розгортання

Пишемо на Python (FastAPI) з PostgreSQL, фронтенд — серверні шаблони з HTMX, усе працює в Docker Compose на наявному VPS під окремим користувачем. Версії бібліотек беремо актуальні стабільні й фіксуємо в lock-файлі.

| Шар | Вибір |
| --- | --- |
| Мова й веб | Python 3.12, FastAPI, Jinja2 + HTMX, без SPA |
| База даних | PostgreSQL, SQLAlchemy 2, міграції Alembic |
| Паролі й сесії | argon2id, серверні сесії в БД, CSRF-токени на кожному POST |
| OCR | Tesseract (pytesseract), Pillow/OpenCV для попередньої обробки, rapidfuzz для нечіткого пошуку назв |
| Проксі | nginx (уже встановлений на сервері), HTTPS через certbot (Let's Encrypt) |
| Тести й лінтер | pytest, ruff |

**Структура репозиторію:**

```text
ohmymatch/
  app/
    main.py            # FastAPI, routes
    config.py          # matching thresholds and weights, limits
    categories.py      # 25 categories, axes, pairs
    parsing/           # text_parser.py, ocr_parser.py
    matching/          # filters.py, scoring.py, explain.py
    contact/           # ContactGateway: зашифрований Telegram-нік, взаємна згода
    models/, db/, templates/, static/
    cli.py             # creating invites
  migrations/
  tests/
  docker-compose.yml
  deploy/nginx.conf.example
  .env.example
```

**Розгортання та ізоляція (контрольний список для VPS):**

- окремий unix-користувач без sudo, окремий користувач Postgres із доступом лише до власної бази;
- rootless-контейнери, власна мережа Docker, застосунок слухає лише `127.0.0.1:8000`, назовні його віддає nginx на 80/443 (налаштований окремо від проєкту, сертифікат через certbot);
- фаєрвол: відкриті 80, 443 і SSH, вхід через SSH лише за ключами, fail2ban;
- нормальний домен замість DuckDNS, HTTPS обов’язковий, HSTS увімкнено;
- секрети (ключ сесій, ключ шифрування контактів `CONTACT_KEY`, токени) лише в `.env` із правами 600 поза репозиторієм; ключ шифрування не потрапляє ні в базу, ні в резервні копії;
- резервні копії шифруються на сервері до надсилання будь-куди (age або gpg), ключ зберігається окремо від копій, ротація — не довше ніж 14 днів.

## 4. Сценарії користувача

Користувач проходить сім кроків від запрошення до метчу й на жодному не вводить нічого, крім вибору зі списків, чисел і пароля.

1. **Вхід за запрошенням.** Введення коду, потім екран «мені є 18» і згода з текстом «що ми зберігаємо». Система пропонує нейтральний нік із генератора (його можна перегенерувати), користувач задає пароль. Надалі вхід лише за ніком і паролем.
2. **Профіль.** «Хто я» (один варіант), «кого шукаю» (кілька варіантів), режим пошуку: звичайний або експериментальний.
3. **Результат тесту.** Дві вкладки: «Вставити текст» і «Завантажити скриншот». Будь-який спосіб приводить до однієї й тієї самої форми з 25 полів, заповненої розпізнаними значеннями. Користувач виправляє помилки й підтверджує. Подробиці в розділі 5.
4. **Список «ні».** Вибір кількох із 25 категорій: чого користувач точно не хоче в партнері.
5. **Стрічка.** Найкращі кандидати з коротким підписом «збіглися за: …» і кнопками «лайк», «пропустити», «більше не показувати».
6. **Взаємний лайк.** Обоє бачать метч у розділі «Метчі». У картці метчу є кнопка «поділитися контактом»: Telegram-ніки обох показуються лише тоді, коли натиснули обоє (розділ 8).
7. **Налаштування.** Змінити режим і «кого шукаю», повторно завантажити результат, виправити список «ні», додати чи прибрати необов’язковий Telegram-нік, видалити акаунт.

## 5. Введення результатів тесту

Обидва способи введення (вставлення тексту й скриншот) дають однаковий результат: словник із 25 категорій із цілими відсотками 0–100, який користувач підтверджує у формі. У базу записуються лише ці 25 чисел; текст, скриншот і посилання не зберігаються.

**Канонічний список категорій** (ключі зберігати в нижньому регістрі, як slug): Switch, Vanilla, Rigger, Non-monogamist, Rope bunny, Dominant, Submissive, Voyeur, Exhibitionist, Experimentalist, Pet, Brat, Owner, Brat tamer, Master/Mistress, Sadist, Slave, Degrader, Masochist, Daddy/Mommy, Primal (Hunter), Degradee, Ageplayer, Little, Primal (Prey). Список живе в `categories.py`, а не розкиданий по коду.

### 5.1. Вставлення тексту (основний спосіб)

Формат: рядок `N% Name`. Решта рядків (посилання, заголовок) ігноруються.

```text
100% Switch
92% Rigger
79% Dominant
```

- Рядок розбирається регулярним виразом на кшталт `^\s*(\d{1,3})\s*%\s+(.+?)\s*$`, пробіли й регістр нормалізуються, юнікодні пробіли та NBSP вважаються звичайними.
- Назва зіставляється з білим списком: спершу точний збіг, потім словник псевдонімів.
- Відсоток поза межами 0–100, невідома категорія, дублікат — помилка зі зрозумілим текстом, нічого не губиться непомітно.
- Якщо знайдено не всі 25 категорій, форма відкривається зі знайденими значеннями, а відсутні поля підсвічуються для ручного введення.
- Посилання на результат (`bdsmtest.org/r/...`) застосунок не відкриває й не зберігає: сторінку малює JavaScript, а скрейпінг чужого сайту не потрібен.

### 5.2. Скриншот (OCR)

Попередження над формою, обов’язкове: «Розпізнавання неточне. Перевір цифри перед збереженням».

- **Ліміти:** до 3 зображень, до 8 МБ кожне, jpeg/png/webp. EXIF видаляти.
- **Попередня обробка:** переведення у відтінки сірого, збільшення у 2–3 рази, автоінверсія темної теми (середня яскравість нижча за половину), адаптивна бінаризація.
- **Розпізнавання:** Tesseract, режим `--psm 6`, виведення через `image_to_data` з групуванням слів у рядки. Кожен рядок проходить той самий розбір, що й текст у 5.1.
- **Назви:** нечітке зіставлення з білим списком через rapidfuzz, поріг збігу не нижчий за 85. Усе, що нижче порогу, позначається як непевне.
- **Непевні значення** (низька впевненість Tesseract, число поза діапазоном, категорія без пари) підсвічуються у формі.
- **Нічого не пишемо на диск.** pytesseract створює тимчасові файли, тому `/tmp` контейнера монтується як tmpfs, а файл видаляється одразу після розпізнавання. Зображення живе лише в пам’яті запиту.
- **Навантаження:** одночасно не більше двох завдань OCR, ліміт запитів на користувача, індикатор очікування на сторінці.

Тестові фікстури OCR генеруються синтетично (PNG з тексту у світлій і темній темі, два масштаби); справжні результати людей у репозиторій не кладемо.

## 6. Модель даних

Схема складається з шести основних таблиць, двох таблиць контакту й таблиці сесій, усі ідентифікатори — випадкові UUID (жодних послідовних id), а всі зв’язки з `users` видаляються каскадно. Зберігається рівно те, що потрібно для підбору та входу.

| Таблиця | Поля | Примітки |
| --- | --- | --- |
| users | id, handle (унікальний нейтральний нік), password\_hash, gender, seeking (набір значень), mode (normal або experimental), focus (nullable, заділ), consent\_version, consent\_at, age\_confirmed\_at, created\_at | немає email, телефону, імені, IP, last\_seen |
| invites | id, code\_hash, expires\_at, used\_by (nullable), used\_at | коди зберігаються лише як хеш |
| test\_scores | user\_id (PK, FK), scores (jsonb: ключ категорії → 0–100), updated\_at | набір ключів перевіряється в застосунку, діапазон — через CHECK |
| dislikes | user\_id, category\_key | PK з обох полів |
| reactions | from\_user, to\_user, kind (like, pass, block), created\_at | PK з пари from і to |
| matches | user\_a, user\_b, created\_at | user\_a менший за user\_b, унікальна пара, створюється в тій самій транзакції, що й другий лайк |
| telegram\_contacts | user\_id (PK, FK), username\_enc (bytea), updated\_at | лише зашифрований токен Fernet; відкритого ніка в базі немає, ключ у змінній середовища `CONTACT_KEY`; FK з `ON DELETE CASCADE` |
| contact\_shares | match\_id (FK), user\_id (FK), created\_at | PK з пари match\_id і user\_id; згода однієї людини на цьому метчі; зникає разом з метчем чи акаунтом (каскад) |

**Індекси:** users(is\_active, gender), reactions(to\_user).

**Сесії:** окрема таблиця sessions (id, user\_id, expires\_at), строк життя обмежений, у разі зміни пароля та видалення акаунта всі сесії стираються.

**Значення gender і seeking:** набір варіантів задається в конфігурації (щонайменше: чоловік, жінка, інше). Орієнтація окремим полем не зберігається, вона випливає з пари «хто я» і «кого шукаю».

**Видалення:** жорстке, без soft delete. `DELETE FROM users` каскадно прибирає рядки в усіх таблицях. З резервних копій дані зникають за ротацією (не довше ніж за 14 днів), і про це прямо сказано на сторінці «що ми зберігаємо».

**Фаза 2 (міграцій зараз не створювати):** match\_feedback (match\_id, user\_id, rating: вогонь, норм, мимо); Telegram-бот (схема в окремому ТЗ). Таблиця контакту з’явилася раніше й, за рішенням власника від 8 листопада 2026, має зовнішній ключ на `users` з каскадним видаленням, щоб видалення акаунта стирало й зашифрований нік.

## 7. Алгоритм підбору

Стрічка будується на льоту: SQL відбирає кандидатів за статтю, Python застосовує решту фільтрів і рахує оцінку, а готові пари заздалегідь не зберігаються. Усі пороги й ваги лежать у `config.py` і змінюються без міграцій.

**Стартові параметри** (підкручуємо з досвідом; це гіпотези, а не наука):

| Параметр | Значення | Зміст |
| --- | --- | --- |
| ACTIVE\_THRESHOLD | 65 | відсоток, від якого інтерес вважається «справді хочу» |
| CURIOUS\_LOW | 30 | нижня межа зони цікавості |
| CURIOUS\_FACTOR | 0.5 | у скільки разів «можу спробувати» важить менше, ніж «хочу» |
| NONMONO\_LOW | 35 | межа «не хочу» для Non-monogamist |
| WEIGHT\_ROLES / WEIGHT\_STYLE (звичайний) | 0.75 / 0.25 | внесок рольової та стильової частин |
| WEIGHT\_ROLES / WEIGHT\_STYLE (експериментальний) | 0.6 / 0.4 | те саме для експериментального режиму |
| FEED\_PAGE\_SIZE | 20 | розмір сторінки стрічки |

### Крок 1. Жорсткі фільтри (взаємні)

Кандидат потрапляє в стрічку, лише якщо виконано всі умови:

1. обидва акаунти активні, і кандидат — не сам користувач;
2. між ними немає реакції block у жодному напрямку, і користувач ще не ставив кандидатові like чи pass;
3. стать кандидата входить у «кого шукаю» користувача, і навпаки;
4. Non-monogamist: відсів, якщо в одного значення не нижче за ACTIVE\_THRESHOLD, а в іншого не вище за NONMONO\_LOW;
5. список «ні»: жодна активна категорія кандидата (не нижче за ACTIVE\_THRESHOLD) не входить до списку «ні» користувача, і навпаки.

### Крок 2. Ефективний профіль

Якщо в людини Switch не нижче за ACTIVE\_THRESHOLD, то в кожній рольовій парі обидві сторони отримують значення max(a, b). Більше ніде Switch участі не бере.

### Крок 3. Осі й пари

| Вісь | Пари (сторона A ↔ сторона B) | Як рахуємо |
| --- | --- | --- |
| Влада | Dominant ↔ Submissive; Master/Mistress ↔ Slave; Owner ↔ Pet | комплементарно |
| Біль | Sadist ↔ Masochist | комплементарно |
| Мотузки | Rigger ↔ Rope bunny | комплементарно |
| Гра | Brat ↔ Brat tamer; Primal (Hunter) ↔ Primal (Prey) | комплементарно |
| Приниження | Degrader ↔ Degradee | комплементарно |
| Опіка | Daddy/Mommy ↔ Little | комплементарно |
| Показ | Voyeur ↔ Exhibitionist | комплементарно |
| Стиль | Experimentalist, Vanilla, Ageplayer | за схожістю |
| Структура | Non-monogamist | лише фільтр (крок 1) |

### Крок 4. Рольова сумісність

Для пари категорій (a, b) і двох людей X та Y рахується краще з двох напрямків. Напрямок робочий, якщо менше з двох значень не нижче за ACTIVE\_THRESHOLD.

```latex
v_p = \max\big(\min(X_a, Y_b),\ \min(X_b, Y_a)\big) \quad \text{(otherwise 0, if the smaller value is below the threshold)}
```

```latex
\text{role\_fit} = \frac{\sum_{p} w_p \, v_p}{\sum_{p \in P} w_p}
```

P — пари, у яких хоча б в одного з двох активна будь-яка сторона. Так людину з вузьким набором інтересів не карають за те, чого в неї немає. Якщо P порожнє, role\_fit дорівнює 0. Ваги пар w\_p за замовчуванням дорівнюють 1.

**Експериментальний режим** додає зону цікавості: якщо більше з двох значень не нижче за ACTIVE\_THRESHOLD, а менше лежить між CURIOUS\_LOW і порогом, напрямок дає CURIOUS\_FACTOR × менше значення. У звичайному режимі такі напрямки дорівнюють 0.

### Крок 5. Схожість стилю

style\_sim — середнє за Experimentalist, Vanilla та Ageplayer від (100 − |X − Y|).

### Крок 6. Підсумок і ранжування

score = WEIGHT\_ROLES × role\_fit + WEIGHT\_STYLE × style\_sim; ваги беруться за режимом того, хто дивиться стрічку. Кандидата показують, лише якщо є хоча б один строго робочий напрямок (не із зони цікавості), навіть в експериментальному режимі. Сортування за спаданням score; за рівності порядок випадковий, але стабільний протягом доби (seed з id користувача й дати). Сторінки по FEED\_PAGE\_SIZE.

### Крок 7. Пояснення в картці

Картка кандидата містить нік і підпис «збіглися за: <назви осей>», до п’яти осей. Для зони цікавості підпис «можна спробувати: <вісь>». Відсотки, конкретні ролі та список «ні» іншої сторони ніколи не передаються ні в HTML, ні в API. Числова оцінка score користувачеві не показується, а інтерфейс каже «збіглися за інтересами», а не «психологічна сумісність»: тест самозвітний.

## 8. Лайки, метчі та обмін контактом

Метч виникає лише за взаємного лайка. Контакт між метчами — це необов’язковий Telegram-нік, який відкривається обом лише за взаємної згоди; Telegram-бот лишається окремим ТЗ.

- **Реакції.** Три види: `like`, `pass` (більше не показувати цю людину), `block` (сховати взаємно й прибрати з метчів). Повторна реакція на ту саму людину замінює попередню, лише якщо це block.
- **Метч.** Коли друга людина ставить like, в одній транзакції створюється рядок у `matches` (пара впорядкована, унікальна). Обоє бачать одне одного в розділі «Метчі».
- **Прибрати метч.** Кнопка «прибрати з метчів» видаляє метч і ставить block з обох боків.
- **Контакт.** Клас `ContactGateway` (`app/contact/`) має метод `on_match(match_id)`, який нічого не робить і лишається точкою підключення бота, а також керує ніком і згодою. Правила нижче обов’язкові.
  - **Нік.** Необов’язкове поле «@нік у Telegram» у налаштуваннях (`POST /account/contact`). Формат: 5–32 символи, латинські літери, цифри й підкреслення, починається з літери, не закінчується підкресленням, без двох підкреслень поспіль; нормалізується до нижнього регістру без `@`. Усе інше відхиляється, а введене значення на сторінці помилки не повторюється. Щоб зберегти нік, треба поставити позначку «розумію, що назад це не відіграти». Порожнє поле видаляє нік.
  - **Зберігання.** Лише в таблиці `telegram_contacts`, і лише як токен Fernet. До відкритого тексту входить id власника, тож токен, скопійований в інший рядок, не розшифровується. Ключ береться зі змінної середовища `CONTACT_KEY`; якщо її не задано, функцію вимкнено (поле й кнопки не показуються, маршрути повертають 404). Нік не потрапляє в журнали, повідомлення про помилки й відповіді API.
  - **Згода.** У картці метчу кнопка «поділитися контактом» веде на сторінку попередження (`GET /matches/{id}/contact`), де сказано: назад не відіграти, друга людина побачить @ і зможе його зберегти назавжди, видалення акаунта цього не скасує, ми не перевіряємо, що @ належить його власнику. Лише після підтвердження `POST /matches/{id}/contact` записує згоду в `contact_shares`. Кнопка доступна, лише якщо в натискача є власний нік.
  - **Показ.** @ обох видно, тільки коли в `contact_shares` є згода обох учасників метчу. До цього друга людина не бачить нічого: ні ніка, ні самого факту натискання (її сторінки не змінюються). Той, хто натиснув першим, бачить лише «згоду записано, чекаємо».
  - **Скасування.** Згоду зняти не можна. Якщо людина змінює або видаляє свій нік, усі її згоди зникають, щоб новий нік не відкрився за старою згодою. Згода зникає також разом із метчем (прибрати метч, блокування) і з акаунтом.
  - **Посилання.** Нік показується як посилання `https://t.me/<нік>` з `target="_blank"` і `rel="noopener noreferrer"`; у посилання потрапляє лише нік, що пройшов перевірку формату.
  - **Без перевірки володіння.** Ми не перевіряємо, що @ належить тому, хто його вказав, і попереджаємо про це в налаштуваннях, на сторінці попередження, в картці метчу, в тексті згоди та на `/privacy`.
- **Сповіщень немає.** Людина бачить метч, коли сама відкриває застосунок.
- **Захист від вивантаження профілів.** Ліміт на кількість сторінок стрічки й реакцій на добу (на старті 100 реакцій і 20 сторінок; зміни ніка — 10 на добу, натискань «поділитися контактом» — 50 на добу), вхід лише за запрошенням, стрічка віддає лише картки з розділу 7, а не сирі дані.

## 9. Приватність і безпека

Головний ризик проєкту — витік бази, бо злив такої бази розкриває людей у їхній власній спільноті. Тому вимоги нижче обов’язкові до виконання, а не побажання.

**Згода, вік, видалення**

- Екран згоди під час реєстрації з текстом «що ми зберігаємо і навіщо» (зокрема про необов’язковий Telegram-нік, його незворотний показ метчу та відсутність перевірки володіння); версія тексту записується в `consent_version`, час — у `consent_at`.
- Позначка «мені є 18», час — в `age_confirmed_at`. Вільного тексту, фото й біографії в MVP немає взагалі: нік генерується зі словника, а єдине поле, яке вводять вручну, — Telegram-нік — відхиляється, якщо не відповідає суворому шаблону.
- Сторінка `/privacy` простою мовою: що зберігається (поля з розділу 6, зокрема зашифрований Telegram-нік і згоди на контакт), як працює обмін ніком (взаємність, незворотність, відсутність перевірки володіння), чого немає (скриншотів, вихідного тексту, email, телефону, імені, IP у БД), як видалити, що копії стираються за ротацією не пізніше ніж за 14 днів.
- Видалення акаунта: кнопка в налаштуваннях, підтвердження паролем, жорстке каскадне видалення, усі сесії анулюються.

**Автентифікація та вебзахист**

- Паролі зберігаються як argon2id. Сесійна cookie: HttpOnly, Secure, SameSite=Lax, обмежений строк. CSRF-токен на кожному POST, зокрема на запитах HTMX.
- Ліміти запитів на вхід, реєстрацію за запрошенням, OCR, стрічку й реакції.
- Сувора Content-Security-Policy, жодних сторонніх скриптів, шрифтів, аналітики й трекерів. Шрифти й скрипти (зокрема HTMX) віддаються з власного домену.
- Сторонні сервіси збору помилок (Sentry і подібні) у MVP не підключаємо.

**Журнали та адміністрування**

- Застосунок журналює лише тип події та ідентифікатор запиту. У журнали не потрапляють відсотки, стать, пари, тіла запитів і параметри рядка запиту.
- Журнали проксі без параметрів запиту, зберігаються не довше ніж 7 днів.
- Вебадмінки в MVP немає. Запрошення створюються командою CLI (`python -m app.cli invite --count N --ttl-days 7`). Через інтерфейс застосунку ніхто, зокрема адміністратор, не бачить чужих профілів.
- Адміністратор може видалити акаунт командою CLI (`python -m app.cli delete-user <handle>`): команда просить ще раз ввести нік для підтвердження й видаляє користувача остаточно, разом з усіма пов’язаними рядками (каскадом).
- Для ручного тесту є демо-користувачі: `python -m app.cli seed-demo --target <нік> --out <файл>` створює шість синтетичних акаунтів `demo_1`…`demo_6` (профілі зашито в код, паролі випадкові й пишуться лише в новий файл із правами 600, на екран виводиться кількість; потрібне підтвердження словом `demo`; `demo_1` ставить лайк акаунту `--target`), а `python -m app.cli delete-demo` каскадом видаляє всіх із префіксом `demo_` і друкує кількість. Зареєструватися з таким ніком не можна, бо нік обирається лише зі згенерованих. Демо-акаунти видно всім у стрічках, тому перед роздачею запрошень їх видаляють.
- Чесне формулювання для користувачів: доступ адміністратора до сервера технічно дає змогу прочитати базу, тому захист розраховано на витік, а не на недовіру до адміністратора.

**Шифрування та резервні копії**

- Паролі зберігаються лише як хеші, коди запрошень теж. Telegram-нік зберігається лише зашифрованим (Fernet), ключ лежить у середовищі застосунку, а не в базі, тож витік бази чи резервної копії нік не розкриває. Адміністратор, який має і базу, і ключ, технічно може його прочитати.
- Диск VPS шифрується, якщо провайдер це дозволяє. Резервні копії шифруються на сервері до надсилання будь-куди, ключ зберігається окремо.

## 11. Нефункціональні вимоги, тести та приймання

Версію прийнято, коли виконано всі пункти контрольного списку нижче, а тести проходять у CI на кожному коміті.

**Продуктивність**

- Стрічка: не довше ніж 500 мс за 1000 активних користувачів.
- OCR одного скриншота: не довше ніж 10 секунд, інтерфейс показує очікування.

**Тести (pytest)**

- **Розбір тексту:** правильний список, сміттєві рядки й посилання, дублікати, пропущені категорії, значення поза 0–100, регістр і зайві пробіли, юнікодні пробіли.
- **OCR:** синтетичні скриншоти (світла й темна тема, два масштаби), розпізнано щонайменше 90% полів, непевні значення позначаються.
- **Підбір:** синтетичні профілі. Взаємність фільтрів, Switch, Non-monogamist, список «ні», зона цікавості, різниця між звичайним і експериментальним режимами, порожній знаменник role\_fit.
- **Інтеграція:** реєстрація за запрошенням, профіль, введення результату, стрічка, взаємний лайк, метч, видалення акаунта.
- **Видалення:** після видалення користувача в базі немає жодного рядка з його id у жодній таблиці, зокрема в `telegram_contacts` і `contact_shares`.
- **Контакт:** формат ніка; у базі лише шифротекст; токен з іншого рядка не розшифровується; до взаємної згоди нік не потрапляє ні в HTML будь-якої сторінки, ні у відповіді, а сторінки другої людини не змінюються від натискання першої; зміна чи видалення ніка скасовує згоди; посилання на t.me з `rel="noopener noreferrer"`; нік не потрапляє в журнали; без `CONTACT_KEY` функція вимкнена.

**Критерії приймання**

- [ ] Двоє людей бачать одне одного в стрічці лише за взаємного виконання фільтрів.
- [ ] Жодна HTML- чи JSON-відповідь не містить чужих відсотків, ролей і списку «ні».
- [ ] Скриншоти й вихідний текст не потрапляють ні в БД, ні у файли на диску (перевірка: після OCR немає нових файлів поза tmpfs).
- [ ] Над формою після OCR завжди видно текст про неточне розпізнавання.
- [ ] У журналах немає полів статі, відсотків і пар, у запитах проксі немає параметрів рядка запиту.
- [ ] Немає зовнішніх скриптів, шрифтів і трекерів, Content-Security-Policy увімкнено.
- [x] Розгортання виконано за контрольним списком із розділу 3, резервна копія шифрується, відновлення з неї перевірено.
- [x] Сторінка `/privacy` відповідає реальній поведінці системи.
- [ ] Telegram-нік нікому не віддається до взаємної згоди ні в HTML, ні в API; після видалення акаунта його рядків у `telegram_contacts` і `contact_shares` немає.

## 12. Порядок робіт і відкриті питання

Роботу ведемо вісьмома етапами; після кожного запускаються тести й робиться коміт, а до наступного етапу переходимо лише за зелених тестів.

1. **Каркас.** Репозиторій, Docker Compose, PostgreSQL, Alembic, nginx, лінтер і тести в CI.
2. **Доступ.** Запрошення через CLI, реєстрація, вхід, сесії, CSRF, 18+ і згода.
3. **Профіль і результат.** Профіль, розбір тексту, форма підтвердження, збереження, список «ні».
4. **OCR.** Попередня обробка, розбір рядків, позначки непевних значень, попередження, тести на синтетичних скриншотах.
5. **Підбір.** Конфігурація, фільтри, оцінювання, стрічка з поясненням, тести за розділом 7.
6. **Реакції та метчі.** Реакції, взаємний метч, сторінка метчів, заглушка ContactGateway.
7. **Приватність.** Сторінка `/privacy`, видалення акаунта, ліміти запитів, заголовки, журнали, скрипт зашифрованих резервних копій.
6а. **Обмін Telegram-ніком.** Необов’язкове поле в налаштуваннях, зашифроване зберігання (`CONTACT_KEY`), `ContactGateway`, кнопка «поділитися контактом» з попередженням, оновлення згоди, `/privacy` і версії згоди, тести. Виконується перед етапом 8.
8. **Розгортання та приймання.** Розгортання на VPS за контрольним списком із розділу 3, прогін критеріїв із розділу 11.

**Відкриті питання** (у MVP прийнято припущення, яке можна змінити без перепроєктування):

| Питання | Припущення в MVP |
| --- | --- |
| Перевірка своїх і видача запрошень | адміністратор вручну роздає одноразові коди через CLI |
| Відновлення доступу | немає: вхід лише за ніком і паролем; хто забув пароль, створює новий акаунт за новим запрошенням |
| Чи потрібен фільтр за містом або регіоном | у MVP немає, гео в схемі відсутнє |
| Точність порогів і ваг | стартові значення з розділу 7, підкручуємо після перших користувачів |
| Зміна списку категорій на bdsmtest.org | розбір падає зі зрозумілою помилкою, список виправляється в `categories.py` |
| Домен | потрібен нормальний домен до розгортання |
| Юридичне опрацювання (дані особливої категорії, ЄС і Україна) | рішення власника до відкриття за межі вузького кола знайомих |
| Telegram-бот і цикл «як усе пройшло» | окреме ТЗ; обмін Telegram-ніком між метчами вже входить у MVP |
| Перевірка, що @ належить людині | немає: застосунок попереджає, що нік не перевіряється; перевірку, якщо потрібна, описує окреме ТЗ |
| Ротація `CONTACT_KEY` | не передбачена: зміна ключа робить збережені ніки нечитабельними, і люди вводять їх знову |
