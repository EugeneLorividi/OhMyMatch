# ТЗ: OhMyMatch MVP (веб, без Telegram)

Oct 18, 2026 · @Lorividi

## 1. Цель и контекст

OhMyMatch — закрытое веб-приложение, которое подбирает людей из одной тусовки друг другу по результатам теста bdsmtest.org. Эта версия ТЗ покрывает только веб-часть; Telegram-бот и контакт между людьми делаются отдельным ТЗ.

- **Аудитория:** закрытая тусовка, порядка сотен пользователей, все 18+.
- **Своего теста нет.** Человек проходит bdsmtest.org и приносит результат: вставляет текст списка или загружает скриншот.
- **Данные особой чувствительности.** Пол, ориентация и интимные предпочтения — персональные данные особой категории. Приложение псевдонимное, а не анонимное, и так же честно называется на странице «что мы храним».
- **Принцип:** храним только то, без чего не работает матчинг. Никаких скриншотов на диске, исходного текста вставки, email, телефонов, фото, био и свободного текста.
- **Платных API не используем.** OCR и парсинг работают локально, без обращения к Claude API и внешним сервисам.

## 2. Границы MVP

В первую версию входит полный путь от регистрации до взаимного метча, без Telegram. Всё, что не вошло, отложено явно, а в схеме данных под него оставлены задел и заглушки.

**Входит:**

- регистрация по инвайту, подтверждение 18+, согласие;
- профиль: «кто я», «кого ищу», режим поиска;
- ввод результата теста: вставка текста и распознавание скриншота, с обязательным подтверждением;
- список «нет» (чего точно не хочу);
- матчинг: жёсткие фильтры, обычный и экспериментальный режимы, объяснение совпадения;
- лайки, пропуск, блок, взаимный метч;
- удаление аккаунта, страница «что мы храним».

**Отложено (не делаем сейчас):**

| Что | Почему отложено | Задел в MVP |
| --- | --- | --- |
| Telegram-бот и контакт | отдельное ТЗ | интерфейс ContactGateway с пустой реализацией |
| Верификация своих | отдельное решение | инвайт-коды через CLI |
| Режим «по поинту» (саб ищет доминанта и т.п.) | дорабатываем после запуска | nullable-поле focus в users, логики нет |
| Цикл «как прошло» после контакта | нужен контакт через бота | таблицу не создаём, описана в разделе 6 |
| Юридическая проработка | решение владельца | страница «что мы храним», согласие с версией |

## 3. Стек, репозиторий и деплой

Пишем на Python (FastAPI) с PostgreSQL, фронт — серверные шаблоны с HTMX, всё в Docker Compose на существующем VPS под отдельным пользователем. Версии библиотек брать актуальные стабильные и зафиксировать в lock-файле.

| Слой | Выбор |
| --- | --- |
| Язык и веб | Python 3.12, FastAPI, Jinja2 + HTMX, без SPA |
| База | PostgreSQL, SQLAlchemy 2, миграции Alembic |
| Пароли и сессии | argon2id, серверные сессии в БД, CSRF-токены на каждом POST |
| OCR | Tesseract (pytesseract), Pillow/OpenCV для препроцессинга, rapidfuzz для нечёткого поиска названий |
| Прокси | Caddy, автоматический HTTPS (Let's Encrypt) |
| Тесты и линт | pytest, ruff |

**Структура репозитория:**

```text
ohmymatch/
  app/
    main.py            # FastAPI, роуты
    config.py          # пороги и веса матчинга, лимиты
    categories.py      # 25 категорий, оси, пары
    parsing/           # text_parser.py, ocr_parser.py
    matching/          # filters.py, scoring.py, explain.py
    contact/           # ContactGateway (заглушка)
    models/, db/, templates/, static/
    cli.py             # создание инвайтов
  migrations/
  tests/
  docker-compose.yml
  Caddyfile
  .env.example
```

**Деплой и изоляция (чеклист для VPS):**

- отдельный unix-пользователь без sudo, отдельный Postgres-пользователь с доступом только к своей базе;
- контейнеры rootless, своя Docker-сеть, наружу торчит только Caddy на 80/443;
- фаервол: открыты 80, 443 и SSH, вход по SSH только по ключам, fail2ban;
- нормальный домен вместо DuckDNS, HTTPS обязателен, HSTS включён;
- секреты (ключ сессий, токены) только в `.env` с правами 600 вне репозитория;
- резервные копии шифруются на сервере до отправки куда-либо (age или gpg), ключ хранится отдельно от копий, ротация не больше 14 дней.

## 4. Пользовательские сценарии

Пользователь проходит семь шагов от инвайта до метча, и ни на одном не вводит ничего, кроме выбора из списков, цифр и пароля.

1. **Вход по инвайту.** Ввод кода, затем экран «мне 18+» и согласие с текстом «что мы храним». Система предлагает нейтральный ник из генератора (можно перегенерировать), пользователь задаёт пароль. Один раз показывается код восстановления.
2. **Профиль.** «Кто я» (один вариант), «кого ищу» (мультивыбор), режим поиска: обычный или экспериментальный.
3. **Результат теста.** Две вкладки: «Вставить текст» и «Загрузить скрин». Любой способ приводит к одной и той же форме из 25 полей, заполненной распознанными значениями. Пользователь правит ошибки и подтверждает. Подробности в разделе 5.
4. **Список «нет».** Мультивыбор из 25 категорий: чего пользователь точно не хочет в партнёре.
5. **Лента.** Топ кандидатов с короткой подписью «совпали по: …» и кнопками «лайк», «пропустить», «больше не показывать».
6. **Взаимный лайк.** Оба видят метч в разделе «Метчи». Кнопка контакта в MVP показывает заглушку «контакт откроется через бота».
7. **Настройки.** Сменить режим и «кого ищу», перезалить результат, поправить список «нет», удалить аккаунт.

## 5. Ввод результатов теста

Оба способа ввода (вставка текста и скриншот) дают один и тот же результат: словарь из 25 категорий с целыми процентами 0–100, который пользователь подтверждает на форме. В базу пишутся только эти 25 чисел; текст, скриншот и ссылка не сохраняются.

**Каноничный список категорий** (ключи хранить в нижнем регистре, как slug): Switch, Vanilla, Rigger, Non-monogamist, Rope bunny, Dominant, Submissive, Voyeur, Exhibitionist, Experimentalist, Pet, Brat, Owner, Brat tamer, Master/Mistress, Sadist, Slave, Degrader, Masochist, Daddy/Mommy, Primal (Hunter), Degradee, Ageplayer, Little, Primal (Prey). Список живёт в `categories.py`, а не размазан по коду.

### 5.1. Вставка текста (основной способ)

Формат: строка `N% Название`. Остальные строки (ссылка, заголовок) игнорируются.

```text
100% Switch
92% Rigger
79% Dominant
```

- Строка разбирается регулярным выражением вида `^\s*(\d{1,3})\s*%\s+(.+?)\s*$`, пробелы и регистр нормализуются, юникодные пробелы и NBSP считаются обычными.
- Название сопоставляется с белым списком точным совпадением, затем через словарь алиасов.
- Процент вне 0–100, неизвестная категория, дубликат — ошибка с понятным текстом, ничего не теряется молча.
- Если найдены не все 25 категорий, форма открывается с найденными значениями, а недостающие поля подсвечены для ручного ввода.
- Ссылку на результат (`bdsmtest.org/r/...`) приложение не открывает и не сохраняет: страница рисуется JavaScript-ом, а скрейпинг чужого сайта не нужен.

### 5.2. Скриншот (OCR)

Предупреждение над формой, обязательно: «Распознавание неточное. Проверь цифры перед сохранением».

- **Лимиты:** до 3 изображений, до 8 МБ каждое, jpeg/png/webp. EXIF удалять.
- **Препроцессинг:** перевод в градации серого, увеличение в 2–3 раза, автоинверсия тёмной темы (средняя яркость ниже половины), адаптивная бинаризация.
- **Распознавание:** Tesseract, режим `--psm 6`, вывод через `image_to_data` с группировкой слов в строки. Каждая строка идёт через тот же разбор, что и текст в 5.1.
- **Названия:** нечёткое сопоставление с белым списком через rapidfuzz, порог совпадения не ниже 85. Всё, что ниже порога, помечается как неуверенное.
- **Неуверенные значения** (низкая уверенность Tesseract, число вне диапазона, непарная категория) подсвечиваются в форме.
- **Ничего не пишем на диск.** pytesseract создаёт временные файлы, поэтому `/tmp` контейнера монтируется как tmpfs, а файл удаляется сразу после распознавания. Изображение живёт только в памяти запроса.
- **Нагрузка:** одновременно не больше двух задач OCR, лимит запросов на пользователя, индикатор ожидания на странице.

Тест-фикстуры OCR генерируются синтетически (PNG из текста в светлой и тёмной теме, два масштаба), реальные результаты людей в репозиторий не кладём.

## 6. Модель данных

Схема состоит из шести основных таблиц и таблицы сессий, все идентификаторы — случайные UUID (никаких последовательных id), а все связи с `users` удаляются каскадом. Хранится ровно то, что нужно для матчинга и входа.

| Таблица | Поля | Заметки |
| --- | --- | --- |
| users | id, handle (уникальный нейтральный ник), password\_hash, gender, seeking (набор значений), mode (normal или experimental), focus (nullable, задел), consent\_version, consent\_at, age\_confirmed\_at, created\_at | нет email, телефона, имени, IP, last\_seen |
| invites | id, code\_hash, expires\_at, used\_by (nullable), used\_at | коды хранить только хэшем |
| test\_scores | user\_id (PK, FK), scores (jsonb: ключ категории → 0–100), updated\_at | валидация набора ключей в приложении и CHECK на диапазон |
| dislikes | user\_id, category\_key | PK из обоих полей |
| reactions | from\_user, to\_user, kind (like, pass, block), created\_at | PK из пары from и to |
| matches | user\_a, user\_b, created\_at | user\_a меньше user\_b, уникальная пара, создаётся в той же транзакции, что и второй лайк |

**Индексы:** users(is\_active, gender), reactions(to\_user).

**Сессии:** отдельная таблица sessions (id, user\_id, expires\_at), срок жизни ограничен, при смене пароля и удалении аккаунта все сессии стираются.

**Значения gender и seeking:** набор вариантов задаётся в конфиге (минимум: мужчина, женщина, другое). Ориентация отдельным полем не хранится, она выводится из пары «кто я» и «кого ищу».

**Удаление:** жёсткое, без soft delete. `DELETE FROM users` каскадом убирает строки во всех таблицах. В резервных копиях данные исчезают по ротации (не дольше 14 дней), это прямо написано на странице «что мы храним».

**Фаза 2 (миграции сейчас не создавать):** match\_feedback (match\_id, user\_id, rating: огонь, норм, мимо), контакт через Telegram (отдельная таблица без внешнего ключа на профиль, зашифрованные идентификаторы, схема в отдельном ТЗ).

## 7. Алгоритм матчинга

Лента строится на лету: SQL отбирает кандидатов по полу, Python применяет остальные фильтры и считает оценку, а готовые пары заранее не хранятся. Все пороги и веса лежат в `config.py` и меняются без миграций.

**Стартовые параметры** (подкручиваем по опыту, это гипотезы, а не наука):

| Параметр | Значение | Смысл |
| --- | --- | --- |
| ACTIVE\_THRESHOLD | 65 | процент, с которого интерес считается «реально хочу» |
| CURIOUS\_LOW | 30 | нижняя граница зоны любопытства |
| CURIOUS\_FACTOR | 0.5 | во сколько раз «могу попробовать» весит меньше, чем «хочу» |
| NONMONO\_LOW | 35 | граница «не хочу» для Non-monogamist |
| WEIGHT\_ROLES / WEIGHT\_STYLE (обычный) | 0.75 / 0.25 | вклад ролевой и стилевой частей |
| WEIGHT\_ROLES / WEIGHT\_STYLE (экспериментальный) | 0.6 / 0.4 | то же для экспериментального режима |
| FEED\_PAGE\_SIZE | 20 | размер страницы ленты |

### Шаг 1. Жёсткие фильтры (взаимные)

Кандидат попадает в ленту, только если выполнены все условия:

1. оба аккаунта активны, а кандидат — не сам пользователь;
2. между ними нет реакции block ни в одну сторону, и пользователь ещё не ставил кандидату like или pass;
3. пол кандидата входит в «кого ищу» пользователя, и наоборот;
4. Non-monogamist: отсев, если у одного значение не ниже ACTIVE\_THRESHOLD, а у другого не выше NONMONO\_LOW;
5. список «нет»: ни одна активная категория кандидата (не ниже ACTIVE\_THRESHOLD) не входит в «нет» пользователя, и наоборот.

### Шаг 2. Эффективный профиль

Если у человека Switch не ниже ACTIVE\_THRESHOLD, в каждой ролевой паре обе стороны получают значение max(a, b). Больше Switch нигде не участвует.

### Шаг 3. Оси и пары

| Ось | Пары (сторона A ↔ сторона B) | Как считаем |
| --- | --- | --- |
| Власть | Dominant ↔ Submissive; Master/Mistress ↔ Slave; Owner ↔ Pet | комплементарно |
| Боль | Sadist ↔ Masochist | комплементарно |
| Верёвки | Rigger ↔ Rope bunny | комплементарно |
| Игра | Brat ↔ Brat tamer; Primal (Hunter) ↔ Primal (Prey) | комплементарно |
| Унижение | Degrader ↔ Degradee | комплементарно |
| Опека | Daddy/Mommy ↔ Little | комплементарно |
| Показ | Voyeur ↔ Exhibitionist | комплементарно |
| Стиль | Experimentalist, Vanilla, Ageplayer | по сходству |
| Структура | Non-monogamist | только фильтр (шаг 1) |

### Шаг 4. Ролевая совместимость

Для пары категорий (a, b) и двух людей X и Y считается лучшее из двух направлений. Направление рабочее, если меньшее из двух значений не ниже ACTIVE\_THRESHOLD.

```latex
v_p = \max\big(\min(X_a, Y_b),\ \min(X_b, Y_a)\big) \quad \text{(иначе 0, если меньшее значение ниже порога)}
```

```latex
\text{role\_fit} = \frac{\sum_{p} w_p \, v_p}{\sum_{p \in P} w_p}
```

P — пары, где хотя бы у одного из двоих активна любая сторона. Так человек с узким набором интересов не наказывается за то, чего у него нет. Если P пусто, role\_fit равен 0. Веса пар w\_p по умолчанию равны 1.

**Экспериментальный режим** добавляет зону любопытства: если большее из двух значений не ниже ACTIVE\_THRESHOLD, а меньшее лежит между CURIOUS\_LOW и порогом, направление даёт CURIOUS\_FACTOR × меньшее значение. В обычном режиме такие направления равны 0.

### Шаг 5. Сходство стиля

style\_sim — среднее по Experimentalist, Vanilla и Ageplayer от (100 − |X − Y|).

### Шаг 6. Итог и ранжирование

score = WEIGHT\_ROLES × role\_fit + WEIGHT\_STYLE × style\_sim, веса берутся по режиму того, кто смотрит ленту. Кандидат показывается только если есть хотя бы одно строго рабочее направление (не из зоны любопытства), даже в экспериментальном режиме. Сортировка по убыванию score, при равенстве порядок случайный, но стабильный в течение суток (seed из id пользователя и даты). Страницы по FEED\_PAGE\_SIZE.

### Шаг 7. Объяснение в карточке

Карточка кандидата содержит ник и подпись «совпали по: <названия осей>», до пяти осей. Для зоны любопытства подпись «можно попробовать: <ось>». Проценты, конкретные роли и список «нет» другой стороны не передаются ни в HTML, ни в API никогда. Числовой score пользователю не показывается, а интерфейс говорит «совпали по интересам», а не «психологическая совместимость»: тест самоотчётный.

## 8. Лайки, метчи и заглушка контакта

Метч возникает только при взаимном лайке, а сам контакт в MVP не реализуется: вместо него стоит интерфейс-заглушка, под которую потом подключится Telegram.

- **Реакции.** Три вида: `like`, `pass` (больше не показывать этого человека), `block` (скрыть взаимно и убрать из метчей). Повторная реакция на того же человека заменяет предыдущую только если это block.
- **Метч.** Когда второй человек ставит like, в одной транзакции создаётся строка в `matches` (пара упорядочена, уникальна). Оба видят друг друга в разделе «Метчи».
- **Убрать метч.** Кнопка «убрать из метчей» удаляет метч и ставит block с обеих сторон.
- **Контакт.** Класс `ContactGateway` с методом `on_match(match_id)`, в MVP он ничего не делает, а на странице метча показан текст «контакт откроется через бота». Никаких ников, юзернеймов и ссылок на мессенджеры в интерфейсе нет.
- **Уведомлений нет.** Человек видит метч, когда сам открывает приложение.
- **Защита от выкачивания профилей.** Лимит на количество страниц ленты и реакций в сутки (стартово 100 реакций и 20 страниц), вход только по инвайту, лента отдаёт только карточки из раздела 7, а не сырые данные.

## 9. Приватность и безопасность

Главный риск проекта — утечка базы, потому что слив такой базы раскрывает людей в их собственном сообществе. Поэтому ниже требования, обязательные к исполнению, а не пожелания.

**Согласие, возраст, удаление**

- Экран согласия при регистрации с текстом «что мы храним и зачем», версия текста пишется в `consent_version`, время в `consent_at`.
- Чекбокс «мне 18+», время в `age_confirmed_at`. Свободного текста, фото и био в MVP нет вообще: ник генерируется из словаря.
- Страница `/privacy` простым языком: что хранится (поля из раздела 6), чего нет (скриншоты, исходный текст, email, телефон, имя, IP в БД), как удалить, что копии стираются по ротации не дольше 14 дней.
- Удаление аккаунта: кнопка в настройках, подтверждение паролем, жёсткое удаление каскадом, все сессии аннулируются.

**Аутентификация и веб-защита**

- Пароли хранятся как argon2id. Сессионная cookie: HttpOnly, Secure, SameSite=Lax, срок ограничен. CSRF-токен на каждый POST, включая запросы HTMX.
- Лимиты запросов на вход, регистрацию по инвайту, OCR, ленту и реакции.
- Строгая Content-Security-Policy, никаких сторонних скриптов, шрифтов, аналитики и трекеров. Шрифты и скрипты (в том числе HTMX) отдаются с собственного домена.
- Сторонние сервисы сбора ошибок (Sentry и подобные) в MVP не подключаем.

**Логи и администрирование**

- Приложение логирует только тип события и идентификатор запроса. В логи не попадают проценты, пол, пары, тела запросов и параметры строки запроса.
- Логи прокси без параметров запроса, хранятся не дольше 7 дней.
- Веб-админки в MVP нет. Инвайты создаются CLI-командой (`python -m app.cli invite --count N --ttl-days 7`). Через интерфейс приложения никто, включая админа, не видит чужие профили.
- Честная формулировка для пользователей: доступ администратора к серверу технически позволяет прочитать базу, поэтому защита рассчитана на утечку, а не на недоверие к админу.

**Шифрование и резервные копии**

- Пароли и коды восстановления хранятся только в виде хэшей, коды инвайтов тоже.
- Диск VPS шифруется, если провайдер это позволяет. Резервные копии шифруются на сервере до отправки куда-либо, ключ хранится отдельно.

## 10. Страницы и эндпоинты

Все страницы, кроме регистрации, входа и `/privacy`, требуют авторизации, а запросы на изменение данных защищены CSRF-токеном. Ответы лент и карточек формируются на сервере и содержат только разрешённые поля.

| Метод и путь | Что делает | Доступ |
| --- | --- | --- |
| GET, POST /register | инвайт-код, 18+, согласие, ник и пароль, показ кода восстановления | гость |
| GET, POST /login; POST /logout | вход и выход | гость, пользователь |
| GET, POST /profile | пол, «кого ищу», режим | пользователь |
| GET /result | страница ввода результата с двумя вкладками | пользователь |
| POST /result/parse-text | разбор вставленного текста, возвращает заполненную форму | пользователь |
| POST /result/parse-image | OCR до трёх изображений, возвращает заполненную форму с пометками | пользователь |
| POST /result/save | сохранение 25 подтверждённых значений | пользователь |
| GET, POST /dislikes | список «нет» | пользователь |
| GET /feed | страница ленты (HTMX-фрагмент для подгрузки) | пользователь |
| POST /react | like, pass или block для кандидата по публичному id | пользователь |
| GET /matches; POST /matches/{id}/remove | список метчей, убрать метч | пользователь |
| GET /privacy | страница «что мы храним» | все |
| POST /account/delete | удаление аккаунта с подтверждением паролем | пользователь |
| POST /account/password | смена пароля | пользователь |

CLI-команда для инвайтов описана в разделе 9. Публичные идентификаторы кандидатов в ленте — случайные UUID, порядковых номеров нигде нет.

## 11. Нефункциональные требования, тесты и приёмка

Версия принята, когда выполнены все пункты чеклиста ниже, а тесты проходят в CI на каждый коммит.

**Производительность**

- Лента: не дольше 500 мс при 1000 активных пользователей.
- OCR одного скриншота: не дольше 10 секунд, интерфейс показывает ожидание.

**Тесты (pytest)**

- **Парсер текста:** корректный список, мусорные строки и ссылка, дубликаты, пропущенные категории, значения вне 0–100, регистр и лишние пробелы, юникодные пробелы.
- **OCR:** синтетические скриншоты (светлая и тёмная тема, два масштаба), распознано не менее 90% полей, неуверенные значения помечаются.
- **Матчинг:** синтетические профили. Взаимность фильтров, Switch, Non-monogamist, список «нет», зона любопытства, различие обычного и экспериментального режимов, пустой знаменатель role\_fit.
- **Интеграция:** регистрация по инвайту, профиль, ввод результата, лента, взаимный лайк, метч, удаление аккаунта.
- **Удаление:** после удаления пользователя в базе нет ни одной строки с его id ни в одной таблице.

**Критерии приёмки**

- [ ] Пара людей видит друг друга в ленте только при взаимном выполнении фильтров.
- [ ] Ни в одном HTML и JSON-ответе нет чужих процентов, ролей и списка «нет».
- [ ] Скриншоты и исходный текст не попадают ни в БД, ни в файлы на диске (проверка: после OCR нет новых файлов вне tmpfs).
- [ ] Над формой после OCR всегда виден текст о неточном распознавании.
- [ ] В логах нет полей пола, процентов и пар, в запросах прокси нет параметров строки запроса.
- [ ] Нет внешних скриптов, шрифтов и трекеров, Content-Security-Policy включена.
- [ ] Деплой выполнен по чеклисту из раздела 3, резервная копия шифруется, восстановление из неё проверено.
- [ ] Страница `/privacy` совпадает с реальным поведением системы.

## 12. Порядок работ и открытые вопросы

Работу ведём восемью этапами, после каждого запускаются тесты и делается коммит, а к следующему этапу переходим только на зелёных тестах.

1. **Каркас.** Репозиторий, Docker Compose, PostgreSQL, Alembic, Caddy, линт и тесты в CI.
2. **Доступ.** Инвайты через CLI, регистрация, вход, сессии, CSRF, 18+ и согласие.
3. **Профиль и результат.** Профиль, парсер текста, форма подтверждения, сохранение, список «нет».
4. **OCR.** Препроцессинг, разбор строк, пометки неуверенных значений, предупреждение, тесты на синтетических скриншотах.
5. **Матчинг.** Конфиг, фильтры, скоринг, лента с объяснением, тесты по разделу 7.
6. **Реакции и метчи.** Реакции, взаимный метч, страница метчей, заглушка ContactGateway.
7. **Приватность.** Страница `/privacy`, удаление аккаунта, лимиты запросов, заголовки, логи, скрипт шифрованных бэкапов.
8. **Деплой и приёмка.** Выкладка на VPS по чеклисту из раздела 3, прогон критериев из раздела 11.

**Открытые вопросы** (в MVP принято допущение, меняется без перепроектирования):

| Вопрос | Допущение в MVP |
| --- | --- |
| Верификация своих и выдача инвайтов | админ вручную раздаёт одноразовые коды через CLI |
| Восстановление доступа | код восстановления, показанный один раз; потерял — создаёт новый аккаунт |
| Нужен ли фильтр по городу или региону | в MVP нет, гео в схеме отсутствует |
| Точность порогов и весов | стартовые значения из раздела 7, подкручиваем после первых пользователей |
| Изменение списка категорий на bdsmtest.org | парсер падает с понятной ошибкой, список правится в `categories.py` |
| Домен | нужен нормальный домен до выкладки |
| Юридическая проработка (данные особой категории, ЕС и Украина) | решение владельца до открытия за пределы узкого круга знакомых |
| Telegram-контакт и цикл «как прошло» | отдельное ТЗ, в MVP только заглушка |
